# 运动世界校园 · 模拟器方案实验记录（无步频版）

> 目标应用：**运动世界校园** `com.zjwh.android_wh_physicalfitness`
> 实验环境：MuMu 模拟器 6.0 / Android 15 (SDK 35) / x86_64 / KernelSU Root + LSPosed(Vector)
> 状态：**定位、轨迹、打卡点、里程、配速全部跑通；步频（60–300 步/分）无法产生 → 成绩判定无效**
> 因此本仓库标题为「无步频版」，用于记录复现步骤与失败根因，供后续研究参考。

---

## 一、结论先看这里

| 判定项 | 模拟器方案结果 | 说明 |
|---|---|---|
| 按顺序通过所有点位 | ✅ 通过 | 5 个打卡点全部命中（田径场 1 号点等） |
| 最少跑 1.00 公里 | ✅ 通过 | 实测累计 1.73 km / 1900 m |
| 配速 2′00″–10′00″ | ✅ 通过 | 实测 6′08″–6′16″/km |
| **步频 60–300 步/分** | ❌ **恒为 0** | 模拟器无计步传感器，模块无法注入 |
| 分段达标 | ❌ 连带失败 | 因步频缺失被判数据异常 |

**根因一句话**：MuMu 的 Android 15 镜像里**只有 3 轴加速度计，没有 `TYPE_STEP_COUNTER` / `TYPE_STEP_DETECTOR`**；
而「随心跑 MokrRun」的步数注入是 **借用系统传感器** 的实现——它 hook `registerListener`，只对注册了 step 类型传感器的监听器推送步数。
没有传感器 → 应用注册不上 → 没有接收方 → 步频恒 0。

详见 [`docs/04-结论-步频为什么是0.md`](docs/04-结论-步频为什么是0.md)。

## 三、这套东西能做什么 / 不能做什么

**能**
- 在 MuMu 里把运动世界启动到「跑步中」界面
- 位置沿自定义路线推进（实测 2.8 m/s 左右），地图上生成真实轨迹
- 5 个官方打卡点按顺序全部命中
- 里程、配速、GPS 质量、电子围栏全部表现正常（服务端判定这些项都通过）

**不能**
- 产生步频/步数（`avgStepFreq` 恒为 0），因此成绩最终被判「数据异常」

## 四、快速开始（复现）

前置：MuMu 模拟器 6.0 已安装、实例为 Android 15、开启 KernelSU 与 ADB。

```powershell
cd scripts
.\00_download.ps1        # 下载 ZygiskNext / Vector / Shamiko / HMA / MokrRun

.\02_modules.ps1         # 安装内核模块并登记到 Vector
.\03_apps.ps1            # 安装目标应用与模块
.\04_hide.ps1            # 环境隐藏
.\05_verify.ps1          # 校验
```

细节与排错见 `docs/01`～`docs/03`。

## 五、为什么最后没走模拟器

同一天内验证了另一条路线：**协议直连**（Python 复现 App 的加密与签名，直接向服务端提交跑步记录）。
那条路上不存在"步频"这个约束——数据由协议按规则生成，四项判定全部通过。
记录见 [`docs/05-协议替代方案.md`](docs/05-协议替代方案.md)。

对比：

| | 模拟器 + 模块 | 协议直连 |
|---|---|---|
| 依赖设备传感器 | 是（所以失败） | 否 |
| 需要 Root/LSPosed | 是 | 否 |
| 步频 | 0 | 正常（按规则生成 230 步/分） |
| 维护成本 | 高（版本一变，hook 全废） | 中（协议版本绑定） |
